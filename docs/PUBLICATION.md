## Подготовка снимка

Нужны Python 3.8 или новее и Git. Из корня проекта:

```bash
python3 tools/publication/prepare.py
```

Для этих служебных скриптов выбран стандартный `unittest`, без внешних библиотек. Это не выбирает тестовый фреймворк будущего приложения. Проверка:

```bash
python3 -B -m unittest discover -s tools/publication -p 'test_*.py' -v
```

Скрипт не использует сеть и не меняет корневую `.git/`. Он читает только публичные файлы из перечня, проверяет локальные ссылки и характерные маркеры секретов, исключения Git и точное соответствие индекса перечню. Неизвестные файлы, личные анкеты и содержимое служебных каталогов не копируются. Проверка маркеров не заменяет просмотр содержания перед публикацией.

В новом исключённом каталоге `tools/publication/.cache/run-…/` сохраняются:

- `repository/`: отдельный Git-репозиторий, ветка `main`, один коммит с публичными материалами, настроенный `origin`;
- `ratatouille.bundle`: переносимая копия этого коммита;
- `issues.json` и `issues/T00.md`–`issues/T15.md`: заголовки, тексты, зависимости и предполагаемые состояния Issues;
- `report.json`: результаты проверок, SHA256 каждого файла и SHA коммита; `published: false` означает, что скрипт не публиковал снимок.

Повторный запуск создаёт новый снимок и сохраняет предыдущий. После изменения публичных документов нужно снова запустить подготовку. Настройки Git задаются только для дочерних команд, глобальная конфигурация не меняется; автор — `Sphag`, адрес коммита — GitHub noreply.

Предполагаемое состояние Issue определяется статусом соответствующей задачи в бэклоге: явно завершённая задача получает `closed`, остальные — `open`. Создание или повторная подготовка снимка сами по себе не изменяют GitHub Issues.

## GitHub CLI и MCP

Встроенный коннектор, отдельный официальный GitHub MCP и GitHub CLI используют разные подключения. Коннектор продолжает возвращать `403 Resource not accessible by integration` при записи; это не проверяет PAT отдельного MCP. Сохранённая авторизация `gh` успешно использована для публикации и создания Issues.

По решению владельца от 8 октября дальнейшая работа с GitHub пока выполняется через `gh`; диагностика удалённого GitHub MCP отложена. MCP-конфигурация и глобальные настройки Git не меняются. GraphQL-запрос через `gh api graphql` подтвердил, что GitHub распознал оба шаблона — «Задача» и «Ошибка» — с правильными названиями, описаниями и разделами. Владелец также подтвердил работу шаблонов в интерфейсе GitHub.

Дополнительная проверка 8 октября установила, что сохранённая авторизация `gh` использует OAuth-токен. Передача этого токена только дочернему процессу позволила проверить адрес MCP без вывода значения и изменения настроек: сервер GitHub MCP вернул `HTTP 403: forbidden: access denied`. Это отдельный отказ для OAuth-токена, а не результат проверки fine-grained PAT владельца. Context7 в той же штатной удалённой проверке прошёл; отчёт сохранён только в исключённом кэше. Причина отсутствия инструментов отдельного MCP в текущем чате пока не установлена.

Затем владелец выполнил `bash tools/mcp/check.sh remote` в своём WSL-терминале с заданным fine-grained PAT. Его отчёт также подтвердил `context7: PASS` и `github: FAIL HTTP 403: forbidden: access denied`. Проверка обычного API с тем же PAT через `GH_TOKEN="$GITHUB_MCP_TOKEN" gh api user --jq .login` вернула `Sphag`: токен работает для GitHub API. Отсутствие переменной в окружении команд помощника не объясняет этот отдельный отказ.

Дополнительные запросы из окружения помощника к MCP `initialize` и `mcp/_ping` без авторизации также вернули 403 с тем же текстом. Это указывает на отказ доступа к адресу сервиса, который не зависит от конкретного переданного токена; конкретная причина на стороне сервиса или соединения пока не установлена. Дополнительные разрешения PAT без основания не запрашиваются. Для сравнения можно проверить `_ping` из другого подключения, например мобильной сети; токен для этой проверки не нужен. Изменение проектной MCP-конфигурации или установка локальной альтернативы требуют отдельного согласования.

Локальный `codex mcp list` видит включённый сервер GitHub, адрес `https://api.githubcopilot.com/mcp/` и `bearer_token_env_var = "GITHUB_MCP_TOKEN"`. Статус `enabled` и способ входа `Bearer token` описывают конфигурацию, а не успешный вызов. Владелец подтвердил наличие переменной в своём терминале и перезапуск клиента. В окружении команд этой управляемой сессии переменной нет, а инструменты отдельного GitHub MCP не переданы чату. Окружение процесса MCP этим не установлено; отсутствие переменной в командной оболочке не доказывает её отсутствие у владельца или у клиента.

Для нового локального запуска с токеном открыть обычный терминал WSL в корне проекта:

```bash
read -rsp 'GitHub MCP token: ' GITHUB_MCP_TOKEN
export GITHUB_MCP_TOKEN
codex
```

После команды `read` вставить токен и нажать Enter; значение не отображается и не записывается в историю. Токен не присылать в чат и не выводить через `printenv`. В локальном клиенте проверить GitHub через `/mcp` и вызов `get_me`. При уже заданном токене повторный ввод не требуется. Служебные настройки из текущей сессии не меняются.

## Привязка текущей папки

Привязка выполнена владельцем 8 октября: подтверждены ветка `main`, upstream `origin/main`, `origin` на `Sphag/ratatouille` и совпадение локального и удалённого коммитов. На момент приёмки `git status --short` был пуст; индекс содержит ровно 30 файлов перечня, личные анкеты и служебные каталоги исключены.

В управляемой сессии корневая `.git/` остаётся доступной только для чтения. Ниже сохранён выполненный владельцем сценарий для **ещё не инициализированной папки**; в текущем связанном проекте его повторять не нужно:

```bash
git init
git symbolic-ref HEAD refs/heads/main
git remote add origin https://github.com/Sphag/ratatouille.git
git -c credential.helper= -c 'credential.helper=!gh auth git-credential' fetch origin main
git reset --mixed origin/main
git branch --set-upstream-to=origin/main main
git status --short
git ls-files
git check-ignore docs/QUESTIONNAIRE.md docs/FOLLOW_UP.md .agents/test .codex/test .aws/test
```

`reset --mixed` устанавливает указатель ветки и индекс из опубликованного коммита, сохраняя все файлы рабочей папки. Локальные отличия останутся видимыми в `git status`. Если репозиторий уже инициализирован, эти команды не повторять вслепую: сначала проверить текущую ветку и `origin`. Личные анкеты и локальные настройки должны остаться исключёнными.

Итоговые документы публикуются через изолированный репозиторий, поскольку помощник не может менять корневые ссылки и индекс Git. После такой публикации владелец может синхронизировать ссылки и индекс из обычного терминала, сохранив содержимое рабочей папки:

```bash
git -c credential.helper= -c 'credential.helper=!gh auth git-credential' fetch origin main
git reset --mixed origin/main
git status --short
```
