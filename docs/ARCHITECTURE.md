# Архитектура и разработка

Реализация T04–T14 слита; локальная приёмка T15 пройдена. Telegram, календарный клиент и VPS сохраняют внешние проверки. Стек и границы ниже отражают текущий код; продуктовые требования — [PROJECT_BRIEF.md](PROJECT_BRIEF.md), проверка — [T15_ACCEPTANCE.md](T15_ACCEPTANCE.md).

## Стек

| Компонент | Выбор | Назначение |
|---|---|---|
| Python | 3.13.16 | Сервер и процесс бота; версия в `.python-version` |
| Зависимости Python | uv 0.12.23, `uv.lock` | Управляемый Python и окружение `.venv` |
| HTTP | FastAPI 0.142.4, Uvicorn 0.54.0 | API и выдача собранного клиента |
| Telegram | aiogram 3.31.0 | Открытие Mini App и напоминания |
| Хранение | SQLite, SQLAlchemy 2.0.54, Alembic 1.20.0 | Модель, внутренние сервисы и миграции T05 |
| Клиент | React 19.3.0, TypeScript 6.0, Vite 8.3.3 | Mini App; точные версии в `frontend/package-lock.json` |
| Node.js | 24.21.0 LTS, npm 11.19.0 | Установка и сборка клиента; используется установка T02 |
| Проверки Python | Ruff, mypy, pytest, httpx2 | Форматирование, линтер, строгая типизация и HTTP-тесты |
| Проверки клиента | TypeScript, ESLint, Prettier | Типы, правила React и форматирование |

Точные версии Python-пакетов фиксирует `uv.lock`, npm-пакетов — отдельный lockfile клиента. Диапазоны в манифестах задают границы будущего обновления; обычная установка использует только lockfile. TypeScript ограничен веткой 6.0 для совместимости с выбранным typescript-eslint. TestClient использует поддерживаемый [Starlette клиент httpx2](https://www.starlette.io/testclient/).

FastAPI выбран для типизированных HTTP-границ и тестирования. React и TypeScript дают единый клиент для будущих форм рецептов, меню и чек-листов. SQLAlchemy и Alembic используются для явной модели и воспроизводимых миграций SQLite. В T05 добавлены внутренние сервисы и расчёты; Основной HTTP-процесс до T11 не обращается к пользовательским данным; T06 добавляет отдельный локальный процесс библиотеки.

## Границы и структура

| Путь | Ответственность |
|---|---|
| `src/ratatouille/` | ASGI-приложение, типы и валидация (`domain.py`), расчёты (`calculations.py`), модели (`models.py`), конфигурация БД (`database.py`) и сервисы (`storage.py`), библиотека (`catalog.py`), ручное меню (`menus.py`), поиск (`generation.py`) и предложения (`proposals.py`), локальные HTTP-адаптеры (`recipe_api.py`, `menu_api.py`, `local_app.py`) |
| `tests/` | HTTP-границы, расчёты, миграции, сохранность снимков, конкурентные изменения и изоляция владельцев |
| `migrations/`, `alembic.ini` | Замороженные схемы Alembic и окружение; `0001` — данные меню, `0002` — учёт импорта библиотеки |
| `frontend/src/` | Русский интерфейс: стартовый экран, формы библиотеки и ручного меню (`MenuPlanner.tsx`, `menus.ts`) и просмотра предложений (`MenuProposal.tsx`) |
| `assets/` | Общие изображения сервиса |
| `data/starter_recipes.json` | Обезличенные стартовые карточки, доступные для импорта после подтверждения |
| `tools/dev/` | Установка uv и команды настройки и проверки приложения |
| `tools/mcp/` | Независимые инструменты помощника, собственный npm-lockfile |
| `tools/publication/` | Проверка явного списка публичных файлов и подготовка Issues |
| `docs/` | Обезличенные требования и документация разработки |

HTTP-процесс принимает запросы по `/api/` и выдаёт сборку клиента по `/` и `/assets/`. Основной процесс содержит `GET /api/capabilities` без личных данных и `GET /api/health` с ответом `{"status":"ok"}`: это проверка работающего процесса. Без сборки клиентской части `/` возвращает 503 с понятным сообщением; неизвестные API возвращают 404.

В T05 реализованы расчёты без HTTP и Telegram, а также транзакционные операции хранения. [Модель и интерфейсы](T05_DATA_MODEL.md) согласованы владельцем: личные данные каждого пользователя, архивирование рецептов и неизменяемые версии. Внешние ключи проверяют владельца связанного объекта; снимки защищены также триггерами SQLite. Для каждого подключения включены внешние ключи и `recursive_triggers`, чтобы `INSERT OR REPLACE` не обходил запрет изменения снимков; план с существующими ревизиями нельзя удалить или заменить. Запись начинается с `BEGIN IMMEDIATE`, а номер черновика и базовая подтверждённая ревизия предотвращают перезапись устаревшими запросами. Проверенная схема транзакций соответствует [документации SQLAlchemy для SQLite](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver).

Значения Decimal хранятся как текст, чтобы SQLite не преобразовывала их в float. Количества делятся на выход рецепта и суммируются как точные дроби; только готовая сумма преобразуется в Decimal. Для периодических дробей используется локальная точность не менее 50 значащих цифр и ROUND_HALF_EVEN; контекст вызывающего кода не влияет на результат. Отдельное округление для отображения пока не добавлено.

В T11 появятся проверка Telegram `initData` перед доступом к пользовательским данным и отдельный процесс aiogram. Сервисы T05 принимают внутреннего владельца и не являются способом HTTP-авторизации; доверенного параметра `user_id` в публичном API нет. В T12 напоминания будут исполняться процессом бота по сохранённому расписанию с Europe/Moscow; до настройки расписание пустое, новые события по умолчанию выключены. Подбор и проверки режимов меню относятся к T08; T05 хранит параметры режимов и рассчитывает фактический состав.

## Запуск

Основная проверяемая среда — Linux x86_64 в WSL. Команды из [README](../README.md) выполняются из корня проекта. Установщик скачивает uv фиксированной версии и проверяет SHA256 архива. uv, его кэш и управляемый Python сохраняются в исключённом `tools/dev/.cache/`; глобальные Python и настройки оболочки не меняются. Node.js требуется версии 24; при отсутствии используется согласованный установщик T02.

Разработка: Uvicorn слушает `127.0.0.1:8000`, Vite — `127.0.0.1:5173` и проксирует `/api/` на сервер. Vite разрешает файловый доступ только к клиенту и общим изображениям. После сборки сервер сам выдаёт клиент. Каталог сборки выбирается переменной `RATATOUILLE_FRONTEND_DIR`, по умолчанию `frontend/dist`. Сборку нужно создать до старта сервера; после пересборки с изменением каталога ресурсов сервер перезапускается.

Для Windows предпочтителен тот же запуск в WSL. Нативный Windows в T04 не проверялся: там потребуются uv 0.12.23, Python 3.13.16 и Node.js 24, установка `uv sync --locked` и `npm --prefix frontend ci`, затем аналогичные команды `uv run` вместо Bash-обёртки. Bash-установщик uv предназначен только для Linux x86_64.

Схема Docker согласована для T14: многоэтапная сборка клиента, Python-образ с готовой сборкой, отдельные процессы web и bot из общего образа; SQLite хранится в постоянном томе. Для Windows Docker запускается через Docker Desktop с WSL, для VPS — через Docker Engine. Контейнеры, Compose и CI реализованы в T14; контейнерная сборка, миграция, перезапуск и backup проверены в GitHub CI. Локально Docker отсутствует; реальный HTTPS/VPS ожидается.

## Конфигурация и проверки

`.env.example` содержит пустой `BOT_TOKEN`, путь к сборке и `RATATOUILLE_DB_PATH=data/ratatouille.sqlite3`. Токен требуется защищённой factory и боту; локальному процессу он не нужен. Файловый BOT_TOKEN_FILE — альтернатива для Compose secret. Переменные передаются процессу через окружение, `.env` автоматически не читается. Секреты, локальные базы, `.venv`, `node_modules`, сборки, отчёты и скриншоты исключены из Git. Личные анкеты не нужны для установки и проверки.

Команда `bash tools/dev/uv.sh run --locked python -m ratatouille.database` создаёт каталог и применяет Alembic до `head`; повторный запуск не меняет данные. Импорт модулей и создание объекта Engine не открывают БД. Миграция содержит собственную схему и триггеры, а не вызов актуального `Base.metadata.create_all`. Начальная обратная миграция `0001` удаляет таблицы и данные, поэтому применяется только к одноразовым тестовым БД; для рабочих данных сначала нужна резервная копия. DBHub к базе приложения не подключался.

`bash tools/dev/check.sh` проверяет Python, запускает HTTP-тесты и тесты публикации, затем проверяет и собирает клиент. Тесты сервера охватывают работу без токена и сборки, корректную выдачу ресурсов, 503, 404 и невозможность выхода из каталога ресурсов. В T05 проверены расчёты, сохранность снимков, черновики, чек-листы и изоляция данных; общий набор T15 содержит 222 теста. Пользовательские сценарии ручного меню и предложений проверены для обоих режимов и длительностей. В управляемой песочнице TestClient и браузеру может требоваться разрешение на локальные сокеты; в обычном WSL-терминале специальная настройка не нужна.

Основания выбора: [uv projects](https://docs.astral.sh/uv/guides/projects/), [управляемые версии Python](https://docs.astral.sh/uv/concepts/python-versions/), [FastAPI testing](https://fastapi.tiangolo.com/tutorial/testing/), [Vite guide](https://vite.dev/guide/), [aiogram](https://docs.aiogram.dev/en/latest/), [SQLAlchemy 2.0](https://docs.sqlalchemy.org/en/20/).

## Библиотека T06

[Реализация библиотеки](T06_RECIPES.md) использует внутренние сервисы T05 и отдельную CLI `python -m ratatouille.local_app`. Команда `--init` явно применяет миграции и сохраняет локальный профиль рядом с БД; обычный запуск требует уже существующий профиль. Рабочая БД и `*.local-owner.json` исключены из Git. Основной `ratatouille.app:app` оставляет личные маршруты закрытыми; клиент выбирает доступный экран через `/api/capabilities`.

Локальный процесс слушает только loopback, не доверяет proxy-заголовкам и проверяет клиентский адрес, Host, Origin и специальный заголовок для изменения данных. Владелец назначается процессом, а не параметром запроса. Это промежуточная граница разработки до Telegram `initData` в T11; она не предназначена для публичного развёртывания.

Карточки T06 валидируются [строгими Pydantic-моделями](https://docs.pydantic.dev/latest/concepts/strict_mode/), а [общая зависимость FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/) проверяет локальный доступ. `Catalog` атомарно сохраняет ингредиенты, версию рецепта и явный допуск; версия вместе с исходными флагами защищает от устаревшей записи. Импорт проверенного набора — одна транзакция, с уникальным учётом владельца и библиотеки; повторный запрос сохраняет пользовательские правки и архив.

Стартовые карточки подготовлены для [проверки владельцем](T06_STARTER_REVIEW.md); согласование КБЖУ не считается медицинским допуском рецепта. Инструкции из источника не дополняются догадками. Импортированным карточкам пользователь отдельно включает допуск к подбору.

## Ручное меню T07

[Контракты и решения T07](T07_MANUAL_MENU.md) используют схему T05 без новой миграции. Список личных планов, атомарные изменения слотов и параметров, проверка недельных повторов и подтверждение подключаются в явном локальном процессе и защищённой Telegram factory. Основной процесс объявляет `recipes: false, menus: false`. Цели плана — отдельный снимок; общие цели задаются для будущих планов. КБЖУ возвращаются точными строками; отклонения не блокируют сохранение. Авторизация Telegram реализована в T11, подбор — в T08.

## Автоматическое предложение T08

[Решения T08](T08_GENERATION.md) используют ограниченный детерминированный поиск без AI. Просмотр не изменяет БД; применение отдельно повторяет проверку текущих допущенных версий, черновика и режима и атомарно заменяет его позиции. Сохранение плана требует подтверждения T07. Поиск выполняется вне транзакции БД, сравнивает точные нормированные отклонения КБЖУ, затем разнообразие текущей и соседней недели. Схема и зависимости не меняются. Личный HTTP остаётся локальным до T11.

## Замена T09

[Контракты T09](T09_REPLACEMENTS.md) пересчитывают все КБЖУ и покупки по фактическому меню. `replacements.py` ограничивает изменения выбранной неделей и фиксирует выбранное блюдо; `generation.improve` принимает заблокированные позиции. `MenuReplacement.tsx` показывает варианты, выбранный сценарий, изменения, покупки и предложение до применения. Сервер заново строит результат перед атомарной записью. Новые зависимости и миграции не добавляются.

## Покупки и готовка T10

[Контракты T10](T10_FULFILMENT.md) выводят расчёты T05 в `fulfilment.py` и `Fulfilment.tsx`. Недельные партии группируются по неизменяемой версии рецепта; покупки — по ингредиенту, совместимой единице и неделе. Отметки сохраняются отдельно от неизменяемого меню, с серверным владельцем и сравнением предыдущего состояния под транзакцией записи. Новая подтверждённая версия не наследует отметки старой.

## Telegram (T11)

`server.py` создаёт защищённое приложение только после проверки настройки. `telegram_auth.py` проверяет подпись и привязывает запрос к UUID владельца через `access.py`; `settings.py` проверяет переменные среды. `bot.py` запускает отдельный polling-процесс с кнопкой. `frontend/src/telegram.ts` подключает тему и сырые данные сессии. Подробнее — [T11_TELEGRAM.md](T11_TELEGRAM.md).

## Напоминания (T12)

`reminders.py` управляет расписанием и долговечными claims доставки. `error_reporting.py` фильтрует логи и ограничивает уведомления владельцу. В `bot.py` worker работает вместе с polling; миграция `0003` создаёт две новые таблицы. `ScheduleSettings.tsx` предоставляет настройку. Правила — [T12_REMINDERS.md](T12_REMINDERS.md).

## Календарь (T13)

`calendar_export.py` создаёт RFC5545 через icalendar и сохраняет последовательность версии в таблице `calendar_versions` (миграция `0004`). Общий `planned_events` читает согласованный снимок в одной транзакции. `CalendarExport.tsx` скачивает авторизованный файл. Правила ручного обновления — [T13_CALENDAR.md](T13_CALENDAR.md).

## Выпуск (T14)

Dockerfile собирает image web/бота с внешним SQLite-томом; compose.yaml и deploy/Caddyfile обеспечивают HTTP/TLS. Workflows ci.yml проверяет приложение и контейнер, release.yml вручную выпускает main через SSH. tools/deploy/ содержит smoke/release; backup.py создаёт согласованную копию. Подробнее — [T14_RELEASE.md](T14_RELEASE.md).
