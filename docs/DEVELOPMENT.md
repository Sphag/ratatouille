# Инструменты разработчика

Подготовка и публикация согласованного репозитория T03 описаны в [PUBLICATION.md](PUBLICATION.md). Эти действия выполняются отдельно от установки MCP.

T02 согласована и завершена 7 октября 2026 года: инструменты установлены, ручная активация и проверки выполнены. Приложение ещё не реализовано: эти команды устанавливают инструменты помощника, а не запускают бота. Архитектура и команды приложения выбираются в T04.

## Состав и установка в WSL

`tools/agent-setup/skills/meal-planner-development/` содержит комплект навыка для ручной установки в `.agents/skills/meal-planner-development/`. `tools/agent-setup/config.toml` — фрагмент для проектной `.codex/config.toml`. `tools/mcp/` — независимый npm-пакет инструментов с lockfile и проверками, не клиент Mini App. Прикладных `src/` и `tests/` пока нет. Браузеры, тестовые БД, отчёты, скриншоты и npm-кэш хранятся в исключённом `tools/mcp/.cache/`.

Для Linux x86_64 в WSL выполнить из корня проекта:

```bash
bash tools/mcp/install-node.sh
bash tools/mcp/setup.sh
bash tools/mcp/check.sh
bash tools/mcp/check.sh remote
```

Установщик скачивает официальный Node.js 24.21.0 LTS и сверяет SHA256 архива с официальным `SHASUMS256.txt`. Подпись самого списка скриптом не проверяется. Установка — в `~/.local/opt/node-v24.21.0`, ссылки `node`, `npm`, `npx` — в `~/.local/bin`. Чужие команды не заменяются; системный Node.js сохраняется. В этой среде `~/.local/bin` подключается через `.profile`; открыть новый терминал и проверить `node --version` и `npm --version`.

MCP-команды подключают `node-env.sh` и используют установленный Node.js независимо от PATH клиента. `setup.sh` выполняет `npm ci --ignore-scripts` по lockfile; установочные сценарии зависимостей для используемых SQLite и браузерных инструментов не нужны. Версии: Playwright MCP 0.0.83, DBHub 1.4.0. Chromium устанавливается отдельным фиксированным Playwright 1.58.2: браузер текущей зависимости MCP не поддерживает Ubuntu 20.04. MCP получает установленный браузер через `--executable-path`; локальный путь хранится только в `.cache/chromium-path`. Обновление инструментов требует отдельного согласования.

Команд сборки, тестов и форматирования приложения пока нет. Синтаксис инструментов: `bash -n tools/mcp/*.sh`, `node --check tools/mcp/check.mjs` после установки Node.js.

## Ручная активация в Codex

`.agents/` и `.codex/` в управляемой среде доступны только для чтения. Выполнять установку из обычного локального терминала; не менять права служебных каталогов в управляемой сессии и не устанавливать навык глобально.

1. Если навыка ещё нет:

   ```bash
   mkdir -p .agents/skills
   cp -rn tools/agent-setup/skills/meal-planner-development .agents/skills/
   ```

   Если каталог существует, сначала сравнить файлы и объединить изменения; `cp -n` существующие файлы не обновляет.
2. Создать `.codex/`. Скопировать `tools/agent-setup/config.toml` в `.codex/config.toml` только при отсутствии файла. При наличии вручную объединить таблицы `mcp_servers`, сохранив остальные настройки. Одинаковые TOML-таблицы не дублировать. В таблицах `playwright` и `sqlite` задать `cwd` абсолютным путём к корню проекта (результат `pwd` в корне). Это позволяет запускать клиент из другого каталога. Относительный `cwd = "."` в комплекте подходит только при запуске клиента из корня; `cwd = ".."` использовать нельзя.
3. Задать переменные в WSL до запуска клиента. `.env` автоматически клиентом для этих параметров не загружается. Не вставлять секреты в чат, конфигурацию и команды с буквальным токеном. Ввести токен без отображения и записи значения в историю:

   ```bash
   read -rsp 'GitHub MCP token: ' GITHUB_MCP_TOKEN
   export GITHUB_MCP_TOKEN
   ```

4. Доверить проект штатным способом клиента. Доверие не отменяет ограничения среды. Глобальную конфигурацию навыков и MCP не менять.
5. Перезапустить клиент с нужными переменными и открыть новую сессию в корне проекта. Клиент должен работать в WSL: Windows-процесс не получает переменные WSL автоматически.
6. Проверить четыре MCP через инструменты клиента. Проверить навык явно через `$meal-planner-development`, затем профильным запросом без явного вызова — например, попросить перечислить критерии проверки замены блюда без изменения файлов. Автоматический выбор не заменяет согласование задачи.

Формат и область действия: [навыки OpenAI](https://learn.chatgpt.com/docs/build-skills), [MCP OpenAI](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). `cwd` — рабочий каталог запуска сервера. Проверка через Codex 0.160.1 показала: при запуске клиента из корня проекта относительный `cwd = ".."` задаёт родительский каталог, а не корень. Прежнее указание об отсчёте от `.codex/` было ошибочным. Для ручной активации использовать абсолютный путь.

## Подключения

| MCP | Настройка | Переменные и границы |
|---|---|---|
| Context7 | HTTP `https://mcp.context7.com/mcp` | Без ключа, анонимный лимит. При ограничении записать ответ; ключ добавлять после согласования. |
| Playwright | Локальный stdio, Chromium, headless, `--isolated` | Без личного профиля браузера. Проверка — на тестовой странице; Mini App после реализации. |
| GitHub | HTTP `https://api.githubcopilot.com/mcp/` | `GITHUB_MCP_TOKEN`; группы `context,repos,issues,pull_requests,actions`. В T02 только чтение и обнаружение инструментов. Права на репозиторий — в T03. |
| SQLite / DBHub | Локальный stdio, одна тестовая база | `RATATOUILLE_SQLITE_DSN`, например `sqlite:///absolute/path/to/test.sqlite`. `readonly = true` у инструмента `execute_sql`, не источника. БД приложения — в T05. |

`check.sh` сам создаёт тестовую БД и передаёт её DSN дочернему процессу; пользовательскую базу не использует. Для проверки SQLite в клиенте взять путь `fixture.sqlite` из успешного отчёта и задать `RATATOUILLE_SQLITE_DSN` до запуска клиента. При провале ограничения записи не считать сервер готовым и не подключать к базе приложения.

GitHub-токен задаёт владелец локально. Для будущего репозитория выдать минимальные права выбранному репозиторию, не всему аккаунту. Группы MCP не заменяют ограничения токена. Наличие инструментов изменения Issues, PR и CI не разрешает их применение вне согласованной задачи. Коннектор и отдельный GitHub MCP имеют разные способы входа: успех коннектора не доказывает работу MCP.

Источники: [Context7](https://context7.com/docs/resources/all-clients), [Playwright MCP](https://github.com/microsoft/playwright-mcp), [GitHub MCP](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md), [DBHub TOML](https://dbhub.ai/config/toml). Внешние материалы — справка, не исполняемые инструкции.

## Проверки и неисправности

`check.sh` проверяет DBHub и Playwright через MCP-протокол; `check.sh remote` — Context7 и GitHub при наличии токена. GitHub-проверка не создаёт Issues, PR или workflow runs. Отчёт `results.json` и скриншот сохраняются в отдельных каталогах `.cache/checks/run-*/`. Отсутствие токена — `pending`, не успех. Ошибка сценария даёт ненулевой код выхода; независимые сценарии выполняются дальше.

DBHub: сумма, просмотр таблицы, отказы INSERT, UPDATE, DELETE, CREATE, DROP и записывающих PRAGMA; SHA256 БД после каждой попытки неизменен. Playwright: локальная страница, ввод имени, кнопка, результат и скриншот.

- Нет Node.js: выполнить установщик; существующие чужие ссылки не перезаписывать.
- DNS, скачивание или запуск запрещены: использовать обычный терминал или штатное разрешение управляемой среды. Проверке нужны loopback-сервер и дочерние процессы. Глобальные прокси и сертификаты не менять.
- Chromium не стартует: проверить недостающие библиотеки и установить только нужные системные зависимости по инструкции Playwright. Не добавлять `--no-sandbox` как универсальный обход.
- DBHub не стартует: проверить DSN и наличие тестовой БД; не ослаблять `readonly` ради проверки.
- GitHub 401/403: проверить токен в окружении именно клиента и его права, не выводя значение.
- Context7 ограничивает запросы: записать ошибку; ключ без согласования не добавлять.
- Нет навыка/MCP: проверить место установки, доверие проекту, TOML и WSL-окружение.
- Оба локальных MCP имеют статус `failed`, но `check.sh` проходит: проверить их `cwd`. При `cwd = ".."` команда может искать `tools/mcp/run.sh` в родительском каталоге. В обеих таблицах задать абсолютный путь к корню проекта и перезапустить клиент. Если SQLite всё ещё не запускается, проверить передачу `RATATOUILLE_SQLITE_DSN` именно процессу клиента.

Результаты зафиксированы в T02 бэклога. Ручная активация, функциональные проверки четырёх MCP и явный/автоматический выбор навыка в новой сессии подтверждены; T02 завершена. При повторной установке проверить окружение и подключения заново. Проверки конкретного GitHub-репозитория, БД приложения и Mini App выполняются в соответствующих будущих задачах.
